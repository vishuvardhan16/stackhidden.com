About

I'm a Software Development Engineer at Amazon Advertising, on the Advertising Analytics and Insights team in New York. For four years I have built the systems that turn raw advertising data into the audience insights advertisers plan campaigns with: the Insights Store platform, the ingestion orchestration service behind it, and the Insights API on top. The pipelines run at petabyte scale, and the hard part is trust: every number has to be traceable back to where it came from.

I design before I build, so the design documents and one-pagers come first. When the team needs something new, I build it end to end, and I stay on call for what I ship. The receipts are on this page: a platform built from scratch, a metadata lookup cut from seconds to milliseconds, an agent program taken from design document to live playbooks.

Case file · Insights platform · 2023 to 2024

Insight Ingestion Orchestration, Built From Scratch

Every insight family on the legacy stack had its own bespoke pipeline. I designed and built the orchestration service the Insights Store now runs on: signal-driven, config-first, and loud when something fails.

8insight families migrated onto it
0 to 1designed and built from scratch
1 SoPconfig-authoring guide, written for the team

The problem

Audience insights (purchase frequency, share of voice, brand switching, demographics, and more) were each computed by their own hand-wired pipeline. Onboarding a new metric meant new code, failures were discovered by customers, and nobody could answer a simple question: what ran, when, and did it publish?

What I built

  • A Coral API gateway with Lambda handlers in front of DynamoDB signal tables that track metrics, subtypes, families, and publishes.
  • A configuration bucket holding auto-deployed JSON configs, so a family is described in config, not code.
  • A work queue with a dead-letter queue and a driver Lambda, plus a Step Function that generates the artifacts each run produces.
  • A Scala Glue payload generator and a signal processor with SNS fan-out, so downstream consumers react to publishes instead of polling.
  • A job metadata table and long-runtime alarms, so a stuck job pages a human instead of stalling quietly.

Decisions

Signals over schedules
Downstream work triggers off publish signals recorded in DynamoDB, not chains of cron timers. If an upstream run is late, downstream waits for the signal instead of computing on stale data.
Config over code
New families and metrics onboard through JSON configuration that deploys itself. I wrote the config-authoring standard operating procedure so the next engineer does not need me in the room.
Fail loud
Dead-letter queues and long-runtime alarms are part of the design, not an afterthought. A failed insight run is a ticket and an alarm, never a silent gap in a dashboard.

Stack: Java (Coral), Lambda, DynamoDB, Step Functions, Glue (Scala), SQS and SNS, TypeScript CDK, Andes 3.0 and Feature Store

Case file · Insights API · 2023 to 2026

The Insights API and Insight Management Service

The serving layer between the insight pipelines and the products that show insights to advertisers. My work here is the unglamorous kind that decides whether a platform feels fast and trustworthy: correct dates, honest availability, and lookups that stay quick as the catalogue grows.

3.7s to ~200msmetadata lookup, reworked end to end
All regionsregionalized integration and load tests
1 APIavailability, counts, and targeted uploads

The problem

Consumers of the Insights Store needed to ask three questions constantly: what insights exist for this advertiser, over what dates, and is the data fresh? Early answers were slow and sometimes wrong, because metric dates were assumed rather than modelled, and metadata reads scanned whole tables.

What I built

  • Cadence-aware metric dates in the Insight Management Service, so weekly, monthly, and quarterly insights each carry their real dates through payloads and API models, with start and end dates supported end to end.
  • A Count API behind the family-availability endpoint, so a UI can show what exists before it asks for the data itself.
  • A targeted family-upload endpoint (Smithy model, data access layer, integration and load tests) for correcting one family without republishing the world.
  • Manual-insights ingestion: an S3-triggered Lambda that assigns IDs, tracks what has been served, and alarms on failure, plus PDF as a supported asset type and a Kinesis dead-letter queue.

Decisions

Fix the access pattern, not the instance
The slow metadata endpoint was reading with a full table Scan. I reworked it to a Query against the right key, which is why the fix held at about 200 milliseconds instead of creeping back.
Dates are part of the contract
An insight without trustworthy dates is a wrong answer waiting to happen. Cadence is modelled in the data, not guessed by each consumer.
Test where it runs
Integration tests are regionalized and load tests run against the real shape of the catalogue, because the failures that matter show up per region and at catalogue scale.

Stack: Java, Smithy, Lambda, DynamoDB, OpenSearch, Kinesis, S3, TypeScript CDK

Case file · Custom brands (ICM) · 2025 to 2026

Bringing Custom Brands Into the Insights Store

ICM brands and business lines did not fit the standard insight model: different brand definitions, different funnels, data living in a separate account. I led the engineering that made them first-class citizens of the Insights Store instead of a side system.

Aug 2025ICM insights live in production
39schedules handed to the incremental refresh starter
4,290lines of legacy code removed
50+change requests for the non-endemic expansion

The problem

Standard insights assume standard brands. Custom brands broke that assumption in the data model, the account mapping, the funnels, and the refresh cycle all at once, and a parallel store would have doubled every future cost.

What I built

  • The low-level design for the integration, then the build: a Yellowtail ECS endpoint reading the sketch database with adaptors for the APT funnel views (trailing twelve months, year to date, quarterly, year-over-year growth).
  • Brand type and version carried in the unified family table and the APIs, with separate S3 partitioning for standard and ICM data.
  • A Step Function and Lambda trigger inside the ICM account, ICM-aware account mapping, and the ICM Purchase Frequency, Demographic, and Recency-Frequency metrics.
  • The incremental refresh system: a starter that decides FULL, INCREMENTAL, or SKIP from the partitions that actually changed, per-configuration refresh records, a no-change-day gate, and one deduplicated ticket per failed run.

Decisions

One family table, two brand types
I extended the unified model with a brand type rather than forking a second store. Every improvement to the platform since then has applied to both brand kinds for free.
Refresh only what changed
Full recomputation on a schedule is simple and wasteful. The starter reads the loyalty partitions and decides per dataset: full, incremental, or skip. On a no-change day the correct amount of compute is none.
Delete as a deliverable
The migration ended with 4,290 lines of legacy OmniFlow code removed. Code that no longer exists cannot page anyone.

Stack: Java, ECS, DynamoDB, S3, Step Functions, Lambda, Zeno, Theta sketches, TypeScript CDK

Case file · Mosaic and Kaleidoscope agents · 2025 to 2026

Agents Over the Data Lake: Mosaic and Kaleidoscope

The current chapter. The audience data behind advertiser insights lives in sketches and data-lake tables that took specialist knowledge to query. The Mosaic program puts AI agents on top of it, with the insights platform as the governed source underneath.

24insights-as-skills playbooks live
13markets in the cold-tier backfill
30 usersgamma load test, passed

The problem

Persona and audience questions ("how big is this audience, in this market, on these devices?") needed sketch data that only a few engineers could reach, and an agent answering those questions needs tools with contracts, not a database connection and good intentions.

What I built

  • Kaleidoscope Data Lake APIs: CreatePersona, DescribePersona, EstimateAudienceSize, DiscoverTables, signal ID resolution, a targeting-expression evaluator, and ephemeral storage, on top of Theta sketch data.
  • The Mosaic audience-strategy agent on Ads Agent Fabric and Bedrock AgentCore Runtime: scaffold, CDK, pipeline, system prompt and response contract, monitoring and alarming, and an agentic sandbox.
  • Insights-as-skills playbooks that package insight logic for the agent, with end-to-end and load testing, and the integration with the internal agent service including a per-realm routing fix for EU and FE.
  • Operations when it counted: recovery from the September 2026 streaming-sketch incident, and an 11-month recency and device-class cold-tier backfill across 13 markets.

Decisions

Insights as skills, not prompts
An agent that improvises an insight is a liability. The platform's insight logic is packaged as tested playbooks the agent invokes, so the answer an advertiser sees is the same computation the platform has always run.
Contracts before autonomy
The agent's response contract, monitoring, and alarms were built with the agent, not after it. Autonomy without observability is just a faster way to be wrong.
Route per realm
EU and FE traffic follows different paths for real regulatory and latency reasons. The routing fix treats realm as a first-class input to the integration, not a special case.

Stack: Python (Strands Agents, FastMCP), Bedrock AgentCore, Java, Theta sketches, DynamoDB, S3, TypeScript CDK
